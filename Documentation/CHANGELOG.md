## 2026-08-29

### Shipped

- **Collections list headings match:** **My Collections**, **Smart Collections**, and **Former Trees** use the same size and weight. My Collections is no longer the small system section header.
- **Duplicate Tree Info:** One name and one function. Add Tree menu and the selected tree both say **Duplicate Tree Info**. New Bonsai Name; botanics, placement, pot, and acquisition are copied. Photos, measurements, and notes stay on the original.
- **My Trees, not In Care:** The active tree list, Dashboard count, Needs Photos empty copy, and Return to My Trees use **My Trees**. Former Trees is unchanged.
- **Bonsai Name is unique:** Add Tree and copy refuse a name already used by any remaining tree (In Care or Former Trees). The form warns while you type a custom name. Delete frees the name; sold or former trees keep theirs.
- **Add Activity is one titled button:** The extra untitled chevron next to **Add Activity** on Tree Detail is gone. The menu is only the labeled button.
- **Today's Work, Needs Repotting, Needs Photos:** Same live membership as Needs Water. **Today's Work** is unique trees from Tasks → Today. **Needs Repotting** is unique trees with a Repotting Task overdue through this month. **Needs Photos** is In Care trees without a photo (same gap as Dashboard → Library).
- **Needs Water matches Tasks:** The Smart Collection lists unique In Care trees that have watering due today — the same Work Types as Tasks → Today (`expires if missed`). Completing watering in Tasks removes the tree here. One tree with morning and evening watering counts as one member.
- **Collections list order:** **My Collections** is first and always open. **Smart Collections** and **Former Trees** are collapsed. Former Trees is last (Died, Sold, Gifted, Donated, Exchanged, Lost). Opening a collection in a collapsed section expands it. Default selection is last opened, then the first My Collection.
- **Deleted Bonsai Names are reused:** Deleting a mistaken tree frees its sequence so the next Add/Copy takes the lowest unused number (no hole at the end of the series). Sold, died, gifted, and lost trees stay in Former Trees and keep their numbers.
- **Add Tree requires Genus and Species:** Save is refused until both are chosen, so a Bonsai Name can always be generated. Same rule as copy — no tree is stored without that identity.
- **Add Tree is a menu:** Global **Add Tree** now opens **New Tree** (blank form) or **Copy Existing Tree…** (pick an In Care tree). The copy is the same as Duplicate Tree. **Duplicate Tree** stays on the selected In Care tree.
- **Duplicate Tree:** Quick Action copies botanics, placement, pot, acquisition, and manual Collections onto a new tree with a newly generated Bonsai Name (same GEN-SPE-CUL-YYYY-NNN rule as Add Tree). If genus/species lookup is empty, Botanical Name or the source’s official name is used. Copy is refused rather than saving a tree with no name. Photos, measurements, notes, and disposal stay on the original. Confirm first. In Care only.
- **Return to Care:** On a Former Tree, Quick Action **Return to Care** warns, then clears the disposal record so the tree is In Care again — lists, Tasks, and Edit come back. History (photos, work, notes) stays.
- **Donated / Exchanged Smart Collections:** Same automatic membership as Died. Collections lists them under Smart Collections; opening one shows every tree with that disposal outcome. Dashboard My Trees already counts them when present.
- **Sold / Gifted / Lost Smart Collections:** Same automatic membership as Died. Collections lists them under Smart Collections; opening one shows every tree with that disposal outcome.
- **Former Trees are view-only:** Tasks, watering, overdue, and notifications skip trees with a disposal method. Tree Detail hides Edit, Add Image, Add Activity, and Add to Collection. Dashboard Library and Trees Requiring Attention count In Care only. Show on Map, View Images, and Delete remain.
- **Former Trees + Died Smart Collection:** Trees with a disposal method leave **In Care** and sit under **Former Trees** (history kept). **Died** is a Smart Collection that fills automatically from Ownership → Died. Dashboard **My Trees** counts In Care first, then Died and Sold (and other outcomes when present). Species breakdown is In Care only.
- **Add to Collection can create a collection:** Tree Detail → Add to Collection now has **+ New Collection…** (same sheet as Add Tree). After Create, the new collection is checked for this tree.
- **Trees list sorts from column headers:** Click Botanical Name, Style, Tree Status, Location, Pot, Acquisition, or Last Repot to sort. Click again to reverse. Acquisition sorts by year (blank last). The toolbar Sort menu is gone — headers are the sort control.
- **Delete Tree works:** Quick Action is live (no longer Coming Soon). Confirm before delete — only for a mistaken or duplicate record, not sold / gifted / dead / lost. The tree leaves the catalog and its Collections; you return to the tree list.
- **Add Tree can keep an existing Bonsai Name:** The name still auto-generates as GEN-SPE-CUL-YYYY-NNN. **Change…** warns that the name is permanent after save, then lets you type the tree’s real code. **Use Generated Name** returns to the rule. Empty override falls back to the generated name. Still locked on Tree Detail after create.
- **Add Tree sheet scrolls only vertically:** The form no longer sits in a 960-pt desktop workspace (the Tree Detail width). Fields stay inside the sheet; you do not scroll sideways to reach pickers.
- **Tree hero stays in its column:** Switching filmstrip photos no longer lets the image’s pixel size widen the photo well over Ownership / Collections / Pot. The 3:4 well is sized from column width; the photo fills and clips inside it.
- **Trees tab crash:** macOS `Table` cells did not inherit `ImageService`, so Botanical Name thumbs fatal-errored (“No Observable object”). The list now passes ImageService in explicitly.
- **Trees tab hang:** Opening Trees decoded every primary photo at full size on the main thread. List thumbs now load off-thread as small ImageIO thumbnails.
- **Tree list thumbnails:** Botanical Name in Trees shows a 3:4 primary-photo thumb (leaf placeholder when missing) so you can spot the tree and who still needs a photo.
- **Portrait photo wells (3:4):** Tree hero, filmstrip, Gallery cards, Image Details, Image Workspace, Location tree thumbs, and Crop Live Preview frames are mild portrait — trees are taller than wide. Not 9:16. Existing crops are unchanged until re-saved in Crop.
- **Independent Live Preview crops:** Tree Thumbnail, Gallery Card, Dashboard, and Collection Card each keep their own pan. Save writes all four. Tree photos use the tree crop; Media → Images uses the gallery crop.
- **Crop Live Preview is interactive:** Click Tree Thumbnail, Gallery Card, Dashboard, or Collection Card to compose that frame (locks aspect). Drag the photo in the frame to pan — the same crop updates on the canvas. Still one presentation recipe.
- **Images grid stays in its cells:** Portrait display crops no longer overflow Media → Images tiles. Thumbnails fill and clip to the card well instead of using the photo’s pixel height as layout size.
- **Tree Image Viewer shows the crop:** Double-clicking a photo on Tree Detail opens the cropped presentation, not the Original. The Original still appears only in Crop Workspace (Media → Images → Crop). Image Workspace and gallery preview follow the same rule.
- **Crop preview matches the frame:** Live Preview and Tree photos now crop pixels from the Original using the same rectangle as the crop box (then fill the card). The old SwiftUI offset math showed a random slice (often the bottom of the photo) and Tree Detail ignored the crop entirely.
- **Crop Workspace actually works:** Save Crop / Reset / Cancel / Compare Original run (window closes on Save and Cancel). Rotate and Mirror still say Coming Soon. Crop handles can be dragged — they were covered by an invisible move-layer.
- **Media Images Crop + hang fix:** Double-click on Media → Images opened Image Workspace without `TaskService` / `WeatherService`, which froze the app. Those environments are now injected. **Crop** is on Image Details and in Quick Actions (select an image first). Crop still changes only the display recipe — the original file is untouched. Gallery tiles show the saved crop.
- **Dashboard “My Trees”:** The Dashboard hero that shows whole-library counts (trees, status, species) is titled **My Trees**, not Collection Summary — so it does not collide with **Collections** (named groups such as Exhibition 2027). Collection Overview, Library, and the Collections module are unchanged.
- **Dashboard portal filled:** My Trees, Weather, and Tasks stay live. **Alerts** (overdue + weather risks), **Upcoming** (week/month/year/next-year counts), **Trees Requiring Attention** (health), **Library** (missing photo/status/species), **Recent Work**, and **Collection Overview** (named Collections) are live and read-only. **Inventory Status**, **Repotting**, and **Quick Statistics** keep their headings with “No function yet.” so gaps stay visible. Today's Care stays hidden (replaced by Tasks). No fake placeholder numbers.
- **Dashboard Tasks card (live):** Overdue count (opens Tasks → Overdue) plus today’s non-watering rows and a single **Watering · N** line (opens Tasks → Today). Read-only: Complete stays in Tasks.
- **Task/Schedule targets — Trees, Location, or Genus:** `AddTaskSheet` gained an **Applies to** section — target any Task or Schedule at specific Trees (multi-select), every Tree at a **Location**, or every Tree of a **Genus** (e.g. "water every Acer the same way", "water everything at Drivhus the same way"). Backed by a new `CareScheduleTarget` enum (`.trees` / `.location` / `.genus`) on `CareSchedule`, replacing the flat `treeIDs` list (existing schedules migrate automatically — a stored `treeIDs` array is read as an explicit Trees target). `.location`/`.genus` targets are resolved fresh every time occurrences are computed (`TaskService.resolvedTreeIDs(for:)`), so a Tree moved into a watered Location, or added to a watered Genus, is covered automatically without editing the schedule. One-off Tasks resolve a target to concrete Tree IDs once, at creation.
- **No double-watering when rules overlap:** When the same Tree is covered by more than one active rule for the same Work Type/fertilizer/day-part at the same time (e.g. an individual-Tree watering rule *and* a Location watering rule that both include it), the Tasks workspace now shows and completes it once, not twice — `TaskOccurrence` gained a de-duplication key (Tree + Work Type + fertilizer + day part) applied across every source (Tasks and Schedules) in `TaskService.pendingOccurrences(due:)`. Completing the single surfaced occurrence still satisfies every rule that produced it, since "last done" is tracked from Work history alone. Automated auto-watering (acting on these rules without a person tapping Complete) remains a distinct future module, not part of Tasks.
- **"Next Year" horizon — future work never disappears:** Tasks gained a fifth horizon, **Next Year**, alongside Today / This Week / This Month / This Year. It surfaces every Task/Schedule's *next* due date once it falls beyond the current calendar year — however far out (e.g. a Scots Pine repotting due in 4 years) — so long-cadence work always has a home in the UI instead of silently having nowhere to show until it's imminent.
- **Task detail sheet + Tree Detail "Upcoming Tasks":** Tapping any row in the Tasks workspace — or the new **Upcoming Tasks** card on Tree Detail — opens a full detail sheet: complete instructions (not truncated the way a list row is), what/who it applies to, cadence and season when it's a recurring Schedule, and an **Open Tree** shortcut when it targets a specific Tree. Tree Detail's new Upcoming Tasks card (placed just before Timeline) lists every Task/Schedule occurrence for that Tree — next due date only, however far out — grouped by Work Type category (Maintenance / Health / Seasonal / Propagation / Styling / Other), reusing the same `WorkTypeCategory` Reference Data already on every Work Type. New `TaskService.pendingOccurrences(forTree:)`. A one-off Task covering several Trees now surfaces once per Tree (mirroring how Schedules already worked) so it appears correctly under every Tree it applies to, not just the first — completing any one of those still completes the whole Task (all Trees) at once, unchanged. View-only for now — editing/deleting a Task or Schedule from the detail sheet is not yet supported.
- **Recurring Complete confirms the next due date:** Completing a recurring Schedule never cancels the rule — it only logs this occurrence and advances the clock. The Undo banner now says so: “Completed … Next due 12 Sep 2026” (or the next remaining time of day for a multiple-times-a-day rule). One-off Tasks keep the shorter “Completed …” message. Pausing or deleting the whole rule remains in **Manage Schedules**.
- **Overdue horizon + missed watering expires:** Tasks gained **Overdue** (sidebar, above Today, with a count badge). Forgotten care that can still be done late (fertilizing, pruning, …) appears **only** there — not mixed into Today / This Week. Work Types gained **Expires if missed** (on for Watering; existing instant-complete types migrate on). Missed watering is deleted (one-off) or catch-up to today (recurring) — never Overdue, never notified. Overdue workspace shows an orange warning when anything is listed.
- **Tree Detail Tasks card (column 3):** The full-width “Upcoming Tasks” band is now a **Tasks** card in the notes column, above Notes. **Overdue** (hidden when empty) sits above **Upcoming**. Category grouping (Maintenance / Health / …) is dropped here — that split belongs in the Tasks workspace. Compact rows (title + date); tap still opens the detail sheet. Missed watering still never appears under Overdue.
- **Watering folded away + A–Z tree pickers:** Routine watering (`expiresIfMissed`) is a collapsed **Watering (N)** disclosure in the Tasks workspace and on Tree Detail → Upcoming, so fertilizing and other work stay visible. Expand to see each tree, sorted by Bonsai Name. **New Task → Applies to → Trees** is also A–Z by Bonsai Name. **Complete All** still completes watering inside the folded group.

## 2026-08-28

### Shipped

- **Work registration (Tree Detail):** Tree Detail → Add Activity → **Work** now registers a real, persisted entry (Work Type + date + notes) via a new `WorkRepository` (CRUD, mirrors Tree/Collection), `LibraryWorkRepository` (`Database/Work.json`), and `PreviewWorkRepository` (pre-Library session). `WorkService` gained `registerWork` / `updateWork` / `deleteWork`; Tree Detail's **Timeline** section now lists real Work history for that tree (chronological, newest first) instead of a placeholder. Location Detail's **Last Work** / **Next Scheduled Work** rows, added in the 2026-08-24 Locations redesign, now populate from real data. Platform-agnostic by design (no SwiftUI/AppKit in the read/write path) so a future Mobile Companion or Windows client can register and read Work through the same contract against the shared Library. Care, Measurements, Photos, Journal, and Documents remain reserved for the same pattern.
- **Fertilizer Types redesigned (Reference Data):** `FertilizerType` is now one entry per fertilizer product the grower actually uses — Name carries product/brand identity (e.g. "BioGold Original"), plus independent **Form** (Granular / Pellet / Liquid / Powder / Tablet / Stick), **Release** (Immediate / Slow Release), **Origin** (Organic / Mineral / Organic-Mineral), and a free-text **NPK** field. Replaces the earlier flat Fertilizer Type + separate Fertilizer Brand lists — one merged, structured entry instead of two disconnected free-text fields. New `FertilizerTypeEditorSheet` in Settings → Reference Data. `AddWorkSheet` shows a Fertilizer picker whenever the selected Work Type is flagged `requiresFertilizer`; the choice carries all its classification automatically via `WorkRecord.fertilizerTypeID` — enables future fertilizing rules per Tree without being locked to flat combinations.
- **Tasks module (minimal, real persistence):** The Tasks workspace (Today / This Week / This Month / This Year) now shows real, persisted `CareTask` entries instead of placeholder cards, via a new `TaskRepository` (CRUD, mirrors Work), `LibraryTaskRepository` (`Database/Tasks.json`), and `PreviewTaskRepository` (pre-Library session). `TaskService` creates, updates, deletes, and completes Tasks. **New Task** opens `AddTaskSheet` (Work Type, tree, due date, title, notes). Completing a Task follows Blueprint §5.9 "Tasks vs. Work": Work Types flagged `tasksCompleteInstantly` (Watering, by default) complete with one click and write a minimal `WorkRecord` automatically via `TaskService.completeTaskInstantly`; every other Work Type opens the full `AddWorkSheet`, pre-filled with the Task's Work Type and Tree, and completes the Task once that Work is saved. Either path writes `WorkRecord.scheduleID` back to the originating Task. Platform-agnostic by design, matching the Work pattern.
- **Recurring care schedules (any Task can repeat):** `AddTaskSheet` gained a **Repeats** toggle — any Work Type can recur every N days/weeks/months/years (daily watering, weekly liquid fertilizer, monthly slow-release fertilizer, every-3-years repotting, annual winter work, …), optionally limited to a season (e.g. no fertilizing before August) via a new `CareSchedule` model. Because a schedule fixes every detail (including which fertilizer) when it's created, its due occurrences always complete in one click — never the Add Work form, even for Work Types that otherwise require it. Due occurrences are computed on demand per (schedule, tree) from the last matching `WorkRecord` plus the interval — no persisted "instance" rows, no daily generation job; logging Work manually through any path still resets the clock. New `ScheduleRepository` (CRUD), `LibraryScheduleRepository` (`Database/Schedules.json`), `PreviewScheduleRepository`, mirroring Task/Work. The Tasks workspace merges one-off Tasks and due Schedule occurrences into one list (`TaskOccurrence`), adds a **Complete All** toolbar action (completes everything that needs no form, reports what's skipped), and a **Manage Schedules** sheet to pause/resume or delete existing rules.
- **Multiple times a day (e.g. watering 2–3x):** A schedule's repeat mode can now be "Multiple times a day" instead of an interval — pick any combination of Morning / Midday / Afternoon / Evening (`CareDayPart`). Due occurrences are the day parts not yet matched by a WorkRecord logged today for that tree, counted in order rather than gated by clock time, so watering slightly early/late or "out of order" still counts correctly. Each due time-of-day shows as its own row (e.g. "Watering — Evening").
- **Toolbar clarity + Undo:** The Tasks toolbar's icon-only buttons (Manage Schedules / Complete All / New Task) now always show their text label next to the icon, not just on hover. Completing a task — single or via **Complete All** — no longer just disappears or shows a dismiss-only alert: a bottom banner reports what happened with an explicit **Undo** button (deletes the WorkRecord(s) just written and puts any one-off Task back to pending), auto-dismissing after a few seconds if left alone.

### Decision

- **Work vs. Task:** `WorkRecord` is the historical log of care that **has been done**; the planned **Tasks** module (Blueprint §5.9, not yet built) owns care that **should be done** — manually planned or, later, automation-generated. `WorkRecord.scheduleID` is reserved to link a completed Work entry back to the Task/schedule that generated it once Tasks ships. **Exception for routine, high-frequency Work Types (starting with Watering):** completing that Task is a single action with no form — it writes a minimal `WorkRecord` automatically (Tree IDs + timestamp, no required notes) so history isn't lost, instead of opening the full Add Work form for something the grower may do daily. Detailed Work Types (repotting, wiring, fertilizing, …) keep the full Add Work flow. Folded into Blueprint §5.9 ("Tasks vs. Work").

## 0.2.0

### Shipped

- Renamed the application’s user-facing identity from Bonsai Hub to **Bonsai World** (UI title, display name, product documentation).
- Adopted the standard Falo sidebar structure: **Workspace**, **Quick Actions**, and **Tools**.
- Introduced reusable `QuickActionsView` with catalog-driven Global and Context actions (New Tree, Search, Import + per-module placeholders). Extend context via `ContextQuickActionsCatalog` without changing the view.
- Toolbar shows the application title **Bonsai World**; sidebar and content use native system backgrounds and shared Falo spacing/typography tokens.
- Locations reference Detail page: structured Header, Summary, Information, related Trees/Collections, Statistics, Notes, and Recent Activity using reusable shared Detail components. Edit opens the existing Location editor sheet; no inline editing or persistence.

### Decision

- Application shell follows Falo Universe Design System navigation and workspace philosophy. Shared shell UI under `Shared/` is structured for reuse by future Falo Worlds; product modules remain World-specific.
- **Physical vs organizational:** Hierarchy is World → Location → Tree. Collections are user-defined groups (many-to-many with trees) and never determine a tree’s Location. Preview collections: Maples, Favorite Trees, Exhibition 2027. Smart collections reserved for later.
- **Collections module (initial):** Sidebar **Collections**, reusable `CollectionsList`, `CollectionDetailView` with member trees, drill-in to `TreeDetailView`. No editing or persistence.
- **Collection membership:** Tree Detail shows memberships and an Add to Collection sheet that toggles PreviewData membership in session; Collection Detail updates immediately. Not persisted.
- **Create Collection:** Sidebar Quick Actions → **New Collection** only; sheet validates name and inserts into PreviewData, then opens the new Collection Detail (starts with zero trees).
- **Reference Data:** Strongly typed master data under `ReferenceData/` seeded verbatim from Excel `Lists` (`Documentation/Project/bonsai_registry_ultimate.xlsx`). Per-list PreviewData files; pickers via `ReferenceDataService`; management via `ReferenceDataManager` (Settings → Reference Data). Style / SizeClass / WorkType / LightCondition / SoilType have no Lists section (empty until edited). No persistence or Excel import.
- **New Tree (UI):** `NewTreeView` sheet from Global Quick Actions; Form sections General / Classification / Growing / History / Notes; all pickers from `ReferenceDataService`. Uses shared `TreeDetailToolbar` (Create mode); Save is a TODO stub.
- **Tree Detail hero:** Sticky 16:9 primary-image hero with empty placeholder and image toolbar (Add / Change Primary / Gallery — UI only). Inspector-style form sections below.
- **Botanical hierarchy:** `Species.genusID` and `Cultivar.speciesID`; `ReferenceDataService.species(for:)` / `cultivars(for:)`; cascading Genus → Species → Cultivar pickers on Tree Detail and New Tree.
- **Automatic naming:** `TreeNamingService.makeBotanicalName` → `Genus Species` / `Genus Species 'Cultivar'`; Tree Detail shows read-only Botanical Name + optional Display Name. Year/sequence reserved for later.
- **Tree Detail fields:** Classification / Growing / History / Notes use `ReferenceDataService` pickers (Style, Size Class, Tree Status, Location, Light Condition, Soil Type, Pot Type, Acquisition Source) plus Acquisition Date and Notes editor. Session-only writes into PreviewData; no persistence or validation. `SoilType` model + empty PreviewData (not on Lists).
- **Tree Detail toolbar:** Shared `TreeDetailToolbar` for Create and Edit — Cancel (leading), Save + More Actions (trailing: Duplicate / Export disabled; Delete disabled in Create). Titles: "New Tree" vs Botanical Name. Save/Cancel are TODO stubs (no persistence).
- **Tree List:** `TreeListView` is the main Trees overview — PreviewData list with thumbnail placeholder, Botanical Name, optional Display Name, Location, and Tree Status. Toolbar: New Tree + Search/Sort placeholders. Selection opens Tree Detail. Empty state offers New Tree via existing Quick Action path.
- **Tree Browser:** `TreeBrowserView` (advanced filters) retained for later; Trees module content column uses `TreeListView`.
- **Tree naming (service prepared):** `TreeNamingService` documents permanent Name rules; imports preserve Names. New Tree workflow does not generate Names yet (UI placeholder).
- **Storage strategy (approved):** Governing strategy lives in Product Blueprint §3 — `StorageProvider` abstraction; Phases 1–4; user-owned library; models store identifiers / relative keys only. Detailed notes: [Architecture/STORAGE_ARCHITECTURE.md](Architecture/STORAGE_ARCHITECTURE.md) (non-governing appendix).
- **Storage foundation (Phase 1):** `Storage/` — `StorageProvider` protocol, `LocalStorageProvider`, `StorageService` (shared + environment). Default library under Application Support. Library location configuration prepared for Settings. No iCloud/OneDrive/Bonsai Cloud providers; no database persistence yet.
- **Image architecture (prepared):** `Images/` — `ImageAsset` metadata model; `Tree.primaryImageID` / `imageIDs`; `ImageService` (metadata + gallery via `StorageService`); library folders `Images/Originals`, `Thumbnails`, `Hero`. No import, thumbnails, or pixel loading yet.
- **Primary image import:** `ImageImportService` — Finder picker (HEIC/JPEG/PNG/TIFF) → copy into `Images/Originals/` via `StorageService` → `ImageAsset` metadata → `Tree.primaryImageID`. Tree Detail Add Image shows the image immediately. No gallery, multi-import, drag & drop, or thumbnails yet.
- **Library management:** `Library` model + `LibraryService` — single local library; create/open/verify folder structure via `StorageService`. No auto-create on launch; `resolveLaunchLibrary()` opens last bookmark or default path when valid.
- **First Launch Wizard:** Welcome screen when no valid library is ready — Create New Library (folder picker → `LibraryService`) or Open Existing Library (validate required folders; clear error if invalid). Extensible option catalog for future iCloud / backup / sample flows.
- **Platform Independence (approved):** Cross-platform readiness is a permanent architectural principle. Ship native macOS first; architecture must support future Windows, iPhone, and Android without major refactoring. Constitution §§10–11; Blueprint §§2 and 6.
- **Tree domain model (complete):** `Tree` is identity + botanical/classification/growing/history IDs + image IDs + relationship ID arrays (collections/projects/journal/tasks) + created/modified dates. No UI, platform, or business logic on the model; related entities by UUID only.
- **Tree repository architecture:** `TreeRepository` protocol + `PreviewTreeRepository` (PreviewData only) + `TreeService` as the sole app-facing Tree API. Views → TreeService → TreeRepository → PreviewData. Persistence backends can replace PreviewTreeRepository later without changing Views.
- **Trees views on TreeService:** `TreeListView`, `TreeDetailView`, `NewTreeView`, `TreeBrowserView`, and `CollectionMembershipSheet` no longer access PreviewData; all Tree reads/writes go through TreeService.
- **Tree Detail View / Edit Mode:** Tree Detail opens in View Mode (read-only, no dropdowns). Edit Mode drafts until Save or Cancel. Botanical identity stays locked. Governing UI rules: Blueprint §6.
- **Trees Quick Actions:** Global — New Tree, Search, Import. Context when a tree is selected — Edit Tree, Add Image, View Gallery, Duplicate, Delete. In Edit Mode context becomes Save, Cancel, Reset Changes. Actions live in Quick Actions only.
- **Workspace Profiles (approved):** One application; Essential / Advanced / Complete control visibility only. Constitution §17; Blueprint §5.
- **Reference Data Manager:** Settings → Reference Data — in-session CRUD. Botanical Library (`BotanicalService`): Genus → Species → Cultivar. Flat lists for other Lists categories. No persistence.
- **Documentation consolidation (approved):** Restored the rule of **exactly five governing documents** (START_HERE, Constitution, Product Blueprint, Falo Design System, Falo Component Library). Product Principles and UI Framework content folded into Constitution and Blueprint; storage strategy summarized in Blueprint §3; `STORAGE_ARCHITECTURE` demoted to `Architecture/` appendix. Roadmap, Changelog, Reviews, and sprint plans remain non-governing.
